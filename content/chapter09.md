# 第09章 AST、遍历与让人看懂的诊断

## 本章目标与前置

前置是会解析表达式和块。本章要设计一份能长期支撑后续阶段的数据结构，并建立足够清晰的诊断。学完后，你应能解释语法树与抽象语法树的区别，选择合理的节点表示，写一次递归遍历，并让错误指回准确的源位置。

AST 是前后端之间的重要契约。设计得当，名字解析、类型检查和代码生成可以各自沿同一棵树工作；设计混乱，则每个阶段都要重新理解源字符串。

## 9.1 为什么要“抽象”

完整语法树会保存文法中的非终结符层级、括号和分号等结构。例如 `1 + (2 * 3)` 可能经过 expression、addition、multiply、primary 等很多层。AST 保留语义需要的结构：一个加法节点，左边是1，右边是乘法节点2与3。括号的作用已经体现为分组，无需一定作为单独节点存在。

```text
Add
  Integer 1
  Multiply
    Integer 2
    Integer 3
```

抽象不等于随意丢数据。如果你要做格式化器、保留注释的重构工具或逐字重建源代码，完整语法树或额外 Token/Trivia 信息可能更合适。本课程的第一任务是检查并编译程序，因此主线 AST 优先保存语义结构与源码位置。

## 9.2 节点至少保存什么

整数节点保存值与来源；变量节点保存名字，解析后还可保存符号编号；二元节点保存运算符、左右孩子与范围；调用节点保存函数名与实参列表；语句节点保存相应表达式或子块。函数节点保存签名与函数体，程序节点保存函数集合。

源码范围可以表示成半开区间 `[begin,end)`：begin 指向第一个字节，end 指向最后一个字节的后一位。半开区间的长度直接是 `end - begin`，空范围也有统一表示。将范围与源文件身份分开保存，后面处理多个文件时就不必把每个节点的文件名字符串重复存很多次。

```cpp
// 教学片段：标签结构体的一种组织方式。
enum class ExprKind { Integer, Boolean, Name, Unary, Binary, Call };

struct SourceRange {
    std::size_t begin;
    std::size_t end;
};

struct Expr {
    ExprKind kind;
    SourceRange range;
    std::string text;
    std::int32_t integerValue;
    std::vector<std::unique_ptr<Expr> > children;
};
```

这是表示方案示例，使用前要补齐构造与字段初始化。`text` 对某些节点是名字，对另一些节点可能是运算符，因此需要清楚的种类约束。一个巨大的“万能节点”若没有不变量检查，会让非法字段组合难以发现。

## 9.3 三种常见表示方案

| 表示 | 优点 | 需要承担的成本 |
| --- | --- | --- |
| `enum class` 加结构体字段 | C++11 直观、分派集中、容易输出 | 要维护字段与种类对应关系 |
| 基类加派生节点 | 每种节点字段清楚，能用虚函数访问 | 虚析构、指针与访问器代码较多 |
| C++17 `variant` | 显式封闭的节点集合，访问时可检查覆盖 | 提高最低标准，递归所有权仍需设计 |

没有一种方案能免去语义设计。Visitor 的价值在于组织操作与节点类型的关系，而不是给所有函数换一个设计模式名字。C++11 主线可以用 `switch` 分派或经典 Visitor；C++17 的 `std::visit` 是可选写法，不应直接放进四标准共用源码。

拥有孩子的指针应表达清楚的所有权。父节点唯一拥有孩子时，`unique_ptr` 很合适。符号表里指向声明的借用指针不应该再拥有同一个节点；否则会重复释放。也可以给声明分配整数 ID，后续统一查询，避免把容器重分配后可能失效的指针到处保存。

## 9.4 先实现一个不会改变树的遍历

最容易验证的 AST 操作是输出树。递归地打印节点种类与缩进，再访问孩子。不要在第一次遍历中同时做类型推导、常量折叠和代码生成；先确认你访问到了正确的所有节点。

```text
dump(node, depth):
    输出 depth 层缩进、节点种类、关键属性
    对每个孩子:
        dump(child, depth + 1)
```

为 `f(1+2, 3*4)` 输出树时，必须保留实参顺序。对于 `if` 节点，应能分清条件、then块与else块，而不是只列三个没有角色的孩子。实际 dump 格式可以使用命名字段，让人读到错误树时能迅速定位是哪一类结构出错。

AST 输出不仅是教学图片，也是调试工具。发现 `1+2*3` 结果错误时，若树已显示乘法在上、加法在下，应先修复解析；若树正确，则继续检查类型、字节码和执行。把阶段结果变得可见，可以避免“每次从头猜”。

## 9.5 递归遍历中的返回值与上下文

不同操作需要不同的信息流。打印函数向下传递缩进深度；类型检查向下传递符号环境，并从孩子向上返回类型；代码生成向下传递当前函数和目标代码缓冲，最终积累指令。这与属性文法中的继承信息、综合信息有自然联系。

不要把所有上下文塞进一批全局变量。处理第二个函数时忘记清空第一个函数的状态，是初学实现中很常见的错误。可以为每个阶段创建对象，将只在一个阶段有效的字段放进去，再为每个函数创建局部上下文。明确状态寿命，比反复“记得清零”可靠。

如果语言允许极端深度的括号或表达式，递归 AST 遍历和析构都可能占用较深宿主栈。教学工具应有输入或深度保护。工业实现还可能使用显式工作栈、arena 分配和迭代遍历。先理解正确性与所有权，再考虑这些工程优化。

## 9.6 诊断由位置、原因和语境组成

看下面的错误程序：

```sprout
fn main() -> int {
    let total = 1;
    print(totel);
    return 0;
}
```

好的诊断能够说明 `totel` 在第3行附近没有声明，并指出它的具体位置。若界面支持源代码片段，可以显示该行与下划线。建议格式如下，具体工具排版可能不同：

```text
example.spr:3:11: error: unknown variable 'totel'
    print(totel);
          ^^^^^
```

为什么在 AST 中保存位置？因为名字解析时，原始 Token 游标早已读到文件末尾；若节点只保存名字，就无法可靠知道这一次使用来自哪里。同一个名字可以出现很多次，仅搜索文本不能确定正确位置。

诊断信息应以用户能行动的事实为中心：“变量未声明”“调用需要2个参数但给了1个”“条件需要 bool，实际为 int”。不要向初学者暴露无关的 C++ 类型名、内部指针或底层异常栈。开发者可以另开调试日志，但不应把日志当作语言错误说明。

## 9.7 恢复与错误节点的取舍

第一版在首个错误处停止，能显著简化不变量：只要后续阶段收到 AST，就认为结构完整。若解析器想报告多个错误，可插入显式 Error 节点，让后续阶段知道它不是真实表达式；或者恢复后继续收集错误，但禁止整个程序进入代码生成。

最危险的做法是遇到错误便返回一个“整数0节点”，不记录失败，然后继续生成并执行。这会把错误程序伪装成合法程序，输出一个毫无依据的结果。恢复的目标是给出更多有用诊断，不是制造一个看似能运行的替代程序。

诊断稳定性也影响测试。测试应该检查错误种类、关键名字和必要位置，不必对每个标点都做精确匹配。否则稍微改善措辞就会破坏大量测试，迫使你保留糟糕表达。

## 9.8 实验与练习

运行 `./sprout --ast` 检查带有函数、if、while和调用的程序。数一数有多少个变量使用节点，再与源代码逐个对应。随后只把一个括号位置改动，观察树中究竟哪条父子关系变化。这个实验训练你把源码表面顺序与树形结构分开理解。
