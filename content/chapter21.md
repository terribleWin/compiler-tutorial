# 21 测试、差分、模糊测试与可信编译

## 学习目标与前置知识

前置是能够独立构建和运行第 20 章工程。本章属于主线验证与进阶测试路线：已有脚本覆盖 VM、静态错误、运行时错误和 C++ 目标；随机生成器、自动缩减器与形式验证属于可以继续完成的扩展。

你要学会区分编译器崩溃、错误接受、错误拒绝、错误代码与资源超限，并知道一个可靠测试结果必须比较什么。测试通过增加信心，但不等于已证明全部输入正确。

## 先建立测试分类

正例验证合法程序的输出与退出状态。负例验证非法程序在正确阶段拒绝，并带合理位置。运行时错误例验证除零、溢出、深度和预算错误受控结束。结构例验证 token、AST 与字节码的关键关系；不必把容易变化的地址编号全部固定死。

| 类别 | 示例 | 核对内容 |
| --- | --- | --- |
| 词法 | 非法字符、关键字边界、CRLF | token 或词法错误位置 |
| 语法 | 缺分号、缺括号、错误表达式 | 拒绝且定位接近问题 |
| 语义 | bool 加 int、名字不存在 | 执行前拒绝 |
| 执行 | 减法、递归、遮蔽、短路 | 打印序列与状态 |
| 保护 | 无限循环、过深嵌套 | 受控诊断，无宿主崩溃 |

测试退出码时不要把 Sprout main 的返回值误当成宿主退出码：当前主线正常执行返回 0，语言 main 的数值结果被忽略。LLVM 直接返回 42 的实验是另一条独立模块实验，不能混用其约定。

## 运行已有回归检查

在 compiler 目录构建后运行：

```text
python tests/run_tests.py ./sprout
python tests/run_tests.py ./sprout --native g++
```

Windows 可把 ./sprout 换成 `./sprout.exe`。第二条还会编译生成目标并比较多个 C++ 标准模式。若工具不可用，应该明确报告缺少哪个工具，不能把没有运行的检查算成通过。修改代码后先跑受影响类别，再跑完整回归，避免每次都用人工操作替代稳定测试。

## 差分测试：两条路线互相检查

同一个确定性的源程序，分别通过 VM 与生成 C++ 的本机程序执行，比较标准输出、错误类别和成功/失败状态。两者不同就有问题，但仅凭不同还不能确定哪条路线错，需要回到规格或第三个参考模型。

两条后端可能共享 Checker、算术辅助规则或 AST，所以一致也不意味着绝对正确：共同 bug 不会被差分发现。可以为小表达式写独立数学模型，用 Python 大整数计算后显式检查 int32 范围，减少共享实现。

资源上限是一个例外边界：VM 按字节码计数，目标程序按检查点计数，接近预算时不承诺在同一步停止。差分样例应远离保护上限，或只比较“受控拒绝”，不要硬要求错误文本和行号完全相同。

## 随机生成合法程序

纯随机字节适合找词法和解析器崩溃；要找错误代码，更有效的是根据文法和类型生成合法 AST，再打印成源码。生成 int 表达式时只选 int 运算，生成 bool 时选比较、逻辑或 bool 字面量。维护可用变量表，避免随机产生未声明名字。

限定深度、数值范围与循环次数，记录随机种子，使失败可重现。第一版只生成纯表达式，之后逐步加局部变量、分支、函数和有限循环。除零与溢出可以作为单独负例类别；对正常结果的差分测试应避免未定义或未约定行为。

本地 Csmith 论文的关键启发正是：测试程序需要明确含义，否则多个结果未必意味着编译器错。不能把随机 C++ 中未规定的实参顺序直接当作 Sprout 的标准答案。

## 变形测试与缩减

没有参考答案时，可以使用应当保持行为的变形：重命名不冲突的局部变量、加入多余括号、用内层独立块包住不逃逸的语句。这些变形仍有前提。例如随意交换两条赋值可能改变依赖；把 x 改写为 `(x+1)-1` 在检查型整数下可能新增溢出。

发现失败后缩减程序：删除函数、删除语句、替换子表达式、减少常量，每次保留原来的失败性质。失败性质应定义清楚，例如“VM 与目标输出不同”，而不是“程序报了某个错”。否则缩减器可能把错误代码问题缩成一个毫不相关的语法错误。

最小复现应附语言版本、工具版本、构建选项、源程序、实际结果、预期结果和稳定复现命令。修复后把它加入测试，才算真正关闭问题。

## 编译器本身的安全与健壮性

源码是不可信输入：超长数字、深括号、长二元链、超大文件、CRLF、注释结尾都值得覆盖。对输入大小、递归深度与 AST 高度分别设限，因为长左结合链即使解析递归不深，也可能生成很深的树。

使用地址/未定义行为检测工具可帮助发现宿主越界与悬垂引用，但支持情况依赖工具链。例如可在支持的 Clang/GCC 环境启用相应 sanitizer 后运行回归。内存检测发现的是编译器实现问题，不等于替代源语言的运行时检查。

## 从测试走向证明与翻译验证

形式验证先为源与目标定义行为，再证明每个 pass 保持关系；翻译验证则对某一次编译的输入/输出检查等价或相容。一个较小入门项目是证明“纯算术表达式编译到栈机后，最终栈顶等于表达式求值”，使用结构归纳即可开始。

测试与证明可以互补。证明依赖规格和可信边界，解析、链接与外部运行时是否被覆盖必须明确；测试可以覆盖未形式化的边界与工具集成。不要把“用了证明助手”当作整个发布链都自动可信。

## 练习、答案与验收

设计十个正常例、十个静态负例、五个运行错误例；为每个写出类别与预期。再为纯表达式随机生成器设定固定种子，对 VM、本机路径和独立模型比较 100 个小样例。
