19 LLVM 与 RISC-V：逐步接入工业工具链#

学习目标与路线选择#

本章是扩展实验；配套 Sprout 主线没有自动发射 LLVM IR 或 RISC-V 汇编。你将先手写一个最小 LLVM 模块，完成验证、优化和本机编译，再理解把现有前端接入 LLVM 要增加什么。LLVM 是工具箱，不会自动替你定义 Sprout 的类型与整数规则。

LLVM 版本、构建选项、C++ API 和命令参数可能变化。先记录 clang --version、llvm-as --version、opt --version，尽量使用同一发行版本的一组工具。官方安装与构建文档 应与所用版本匹配。主线编译器兼容 C++11，不表示新版本 LLVM 开发库本身也能用 C++11 构建；可以把 LLVM 后端做成需要较新标准的独立扩展目标。

最小 LLVM 模块#

保存为 answer.ll。它不依赖 print，直接返回 42，便于先排除运行时链接干扰。

define i32 @answer() {entry:  %x = add i32 40, 2  ret i32 %x}define i32 @main() {entry:  %r = call i32 @answer()  ret i32 %r}

% 前缀表示局部 SSA 值或相关局部名字，@ 前缀表示全局符号。entry 是块标签。每个块有终结指令，i32 明确整数宽度。这里的 add 只是一个特定 IR 操作，不自动带 Sprout 溢出诊断。

在安装对应工具后执行：

llvm-as answer.ll -o answer.bcopt -passes=verify -disable-output answer.bcopt -S -passes=instcombine answer.ll -o answer.opt.llclang answer.ll -o answer

运行 answer 后，在类 Unix shell 中查看 $?，PowerShell 中查看 $LASTEXITCODE，应为 42。因为本实验没有输出，屏幕空白并不是没运行。Windows 可让输出名为 answer.exe。命令语法按匹配版本的 opt 手册确认。

分支和 φ 的对应关系#

把条件分支写成 br i1 %cond, label %left, label %right，汇合块使用 φ 表达来自不同前驱的值。φ 应位于块开头，并为对应前驱提供输入。第 15 章的手算此时转成系统可验证的格式。先写一个 if 返回 4 或 6 的独立函数，使用常量条件调用两次，确认行为，再开始写 AST 发射器。

验证器能发现结构与类型问题，却不能证明你忠实实现了 Sprout。例如把减法左右操作数写反，LLVM IR 仍可能完全合法。这就是“目标表示合法”和“翻译语义正确”的区别，必须分别测试。

可变变量的两种接入策略#

一条路线是直接构造 SSA，使用自己的 CFG、支配和 φ 算法；另一条是先为局部变量生成 alloca/load/store，再让合适的提升 pass 转成 SSA。后者更适合初次接入，但仍需理解地址是否逃逸、变量布局及提升条件，不是所有内存都能变成寄存器。

若用文本发射，第一版只需管理唯一名字、类型、块和前驱关系，避免立刻引入开发库链接问题。之后改用 IRBuilder 可以获得更好的 API 组织与类型帮助。两条路线都应在每个函数生成后调用或运行验证器，并保留可读 dump。

保留 Sprout 的检查型算术#

最容易出现的严重错误是把所有加法直接改为 add nsw i32，以为 nsw 表示“帮我检查溢出”。它表示优化所依赖的语义承诺，绝不是用户友好的检查指令。若承诺被破坏，不能期待得到与主线一致的报错。

可使用带溢出结果的 intrinsic，或扩展到 i64 计算后比较范围，再分支到错误处理。除法在发出前检查除零与最小整数除以 -1。print 可以接一个自己的 C ABI 运行时函数，避免在第一版里同时处理 printf 的可变参数与平台差异。LLVM 语言参考 是确认每个操作含义的依据。

从 LLVM 到 RISC-V#

LLVM 能为已构建的目标生成代码，但目标架构、目标三元组、ABI、系统库和链接器需相互匹配。仅指定 RISC-V 指令集，不意味着本机就能直接执行生成文件。交叉编译需要对应 sysroot/运行时；运行需要真实硬件或合适模拟器。

先选一个明确环境，例如 RV64 Linux 用户态，避免混用裸机启动与 Linux 系统调用。先用交叉 C 工具链编译最小 C 程序并运行，证明环境可用；再让 LLVM 输出同目标的目标文件；最后链接 Sprout 运行时。每次只增加一个未知因素。

RISC-V 学习顺序建议是寄存器与整数指令、load/store、分支、函数与 ABI、对象文件、模拟运行，再研究压缩指令、向量或特权架构。用户态编译器入门无需先通读所有特权手册。资料库中多个年份的 ISA 文件应视为历史版本，实际工具参数要按目标版本核对。

MLIR、AI 编译器与多层表示#

若语言增加张量，高层的“矩阵乘法”过早降成标量 load/add，会失去形状、布局与并行结构。多层 IR 可以先保留领域操作，做形状推导、算子融合、分块等变换，再逐级降到循环与机器相关表示。MLIR 的 dialect 是表达这种分层的一种机制。

这与“用机器学习帮助编译器决定优化策略”是不同方向：前者是编译机器学习程序，后者是机器学习用于编译器。两者都建立在前端、IR、正确性与测量基础上。MLIR 官方 Toy 教程 可作一个后续项目，不必在第一次成功运行 Sprout 前引入。

练习与验收#

先把 answer 改成两参数 add 函数，再增加 if。故意让 φ 缺一个前驱，观察验证器。最后设计一个能区分“检查溢出”和“无检查回绕”的边界样例，说明扩展后端该怎样运行它。

参考答案

函数参数应明确声明 i32，调用时传递匹配类型。φ 必须对应实际进入边；缺项属于结构错误。边界样例可取最大 int32 加一，Sprout 语义应报错；直接 add 的结果规则与 nsw 承诺都不能替代运行时检查。验收记录工具版本、模块验证、正常调用结果、错误行为与跨目标运行环境，不能只交一个看起来像 IR 的文本文件。
