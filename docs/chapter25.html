CHAPTER 25 / AI 专题

第25章 AI辅助编译：自动调优、学习式优化与验证#

本章目标与实现边界#

前两章讨论怎样把 AI 模型变成可执行程序。本章反过来问：编译器面对很多合法实现时，能不能利用测量、机器学习或大语言模型，更快找到合适的实现？学完后，你应能设计一个有明确预算的搜索实验，区分训练、验证与测试，解释 e-graph 的作用，并为模型提出的优化安排独立验证。

前置知识是第 14—17 章的数据流、SSA、优化和寄存器分配，以及第 21 章的差分测试。本章是新增的高级扩展专题。现有 Sprout 编译器没有 MLGO、学习式代价模型、e-graph 或 LLM 优化器，也没有张量调度接口。配套新增 Python 实验独立演示研究流程，不会改变 Sprout 的语法、int32 检查或两个既有后端。

25.1 先分清两个方向#

问题 Compilers for AI：为 AI 编译 AI for compilers：用 AI 帮助编译
被处理的主要对象 神经网络、张量图和算子程序 编译器要做的选择或程序变换
典型任务 图优化、算子融合、布局与设备映射 预测内联收益、调度排序、优化序列选择
AI 模型的位置 模型是输入程序 模型是编译器内部或旁边的决策工具
核心正确性问题 目标程序是否实现原模型允许的数值行为 被选方案是否合法、是否保持源程序语义

两个方向可以相交：张量编译器可以用学习式代价模型挑选分块方案。但它们没有互相包含的关系。编译神经网络不要求优化器本身一定使用神经网络；用模型改善普通 C 函数内联，也不意味着这个 C 程序在执行 AI 推理。

对新手最重要的连接是：前面学过的规范、类型、数据流和测试仍然有效。模型可以给候选方案打分，却不会自动保证候选满足类型、依赖、别名、溢出或 ABI 条件。先定义合法候选，再讨论谁更值得尝试，整个系统会清楚得多。

25.2 先问“能不能”，再问“值不值”#

以矩阵乘法为例，循环交换、分块和向量化可以形成许多版本。若两个循环之间有真实数据依赖，就不能仅因预测更快而交换；若一个版本遗漏边缘块，它即使跑得非常快，也是在少算数据。合法性属于语义分析，性能属于代价评估，两个接口应分开。

可以把优化任务写成：在合法集合 S 中、预算 B 内，寻找使目标代价较低的候选 s。目标可能是运行时间、目标文件大小、峰值内存、编译时间，或它们的受约束组合。某方案减少代码大小却增加运行时间时，不能笼统地称为“更优”，必须说明本次目标。

还要计算调优成本。假设额外搜索花费 30 秒，每次执行只节省 1 毫秒，那么需要约 30000 次执行才能抵消搜索开销，且这还没有包含部署等其他成本。总成本可近似写为 调优时间 + 执行次数 × 单次执行时间。长期复用的服务和只运行一次的小程序，合理预算可能完全不同。

失败也要有类型：结构无效、验证不通过、编译超时、执行超时、性能不佳是不同结果。不能把错误程序的异常快速退出记成最佳性能，也不能把测量超时随意改成一个特别小的数。

25.3 从传统代价模型走到搜索#

传统模型根据指令数、估计延迟、内存访问、寄存器压力和分支等信息计算代价。例如一个内联启发式可同时考虑调用开销、函数体大小和调用位置；一个循环模型可估计工作集与缓存关系。这类模型通常便宜、容易解释，但很难精确覆盖所有微架构和程序交互。

搜索负责决定测哪些候选，代价模型负责估计候选好坏。二者不是同一个模块。第一版可以穷举一个很小的参数集，建立基线；候选多了再用随机搜索、局部搜索、束搜索或贝叶斯优化等方法。不要因为方法名字先进，就跳过与简单基线的同预算比较。

真实测量最接近当前目标，却比较昂贵。常见做法是先用静态规则排除非法或明显不合适者，再用模型排序，只编译和测量少量有希望的方案，然后把测量结果补入数据。这里既需要“利用”已知好区域，也需要适度“探索”模型不确定的区域，否则可能永远看不到更好的候选。

学习式代价模型可以预测耗时，也可以只学习相对排序。对选最优候选的任务，前几名的排序常比所有样本上的平均预测误差更有用。论文《Learning to Optimize Tensor Programs》以统计代价模型引导张量程序实现搜索，是理解这一接口的原始研究入口；其历史实验结果不能直接当作当前机器上的性能承诺。原论文

25.4 MLGO：替换一个启发式，不是替换整个编译器#

截至本章核对的 LLVM 官方 MLGO 文档，列出的集成方向是以代码大小为目标的内联，以及以性能为目标的 LLVM 贪心寄存器分配驱逐启发式。其中 eviction 是决定为新分配腾出空间时如何处理已有分配，不能扩大表述成“模型已经负责全部寄存器分配”。LLVM MLGO 官方文档

可以把这种接入理解为一个局部接口：编译器提取特征，模型给出建议，现有优化器继续实施对应操作。研究者仍须评估模型目标、特征有效性、推理开销和失效后的行为。模型预测的是某种训练目标下的选择质量，不是在重新定义源语言。

官方文档也明确说明，组织训练的工具不属于 LLVM 核心的一部分；LLVM 提供与训练配合的设施。不要把“LLVM 中存在接口”理解为本机安装的任意 clang 已经带有所需模型、训练环境或相同构建选项。实践时记录 LLVM 版本、构建配置和模型版本，按对应文档核对；本章没有要求为运行小实验而编译整套 MLGO。MLGO 的训练边界说明

为 Sprout 做第一个类似实验时，可以从一个极小选择开始，例如在两种已验证的表达式发射方案之间排序。先保持 Checker 和算术规则不变，再将“选择谁”抽成接口。先有可替换的普通策略，模型加载或预测不可用时才有清楚的回退基线。

25.5 学到的代价为什么会失效#

一个样本不只是“程序”和“时间”。至少还应包含形状、数据类型、布局、目标硬件、编译器版本、编译选项及测量条件。相同 IR 在不同缓存、向量能力或内存带宽条件下，优选方案可能不同。换硬件后继续使用旧模型，是需要评估的迁移，而不是天然成立的泛化。

训练集用于拟合参数；验证集用于选超参数、选策略或决定是否接受模型；测试集用于最后一次评估已冻结方案。若看到测试结果不好后又改特征、调阈值、重新选方案，这批测试数据已经参与开发，应另留新的最终测试集。

编译数据特别容易泄漏。同一个函数只换变量名、同一模型只换少量尺寸、同一项目的近似版本，可能被随机分到训练和测试两边。模型看似处理了新程序，实际是在认出近亲。应按项目、算子家族、来源版本或形状家族分组，并说明当前划分到底检验哪一种泛化。

硬件泛化和程序泛化也应分开：在同一 CPU 上测试未见形状，不证明换一台设备仍有效；在新硬件上重测相同几个程序，也不证明能处理新项目。报告时把“同分布测试”“新形状”“新程序家族”“新硬件”分项呈现，结论才有边界。

25.6 可运行实验：让测量、学习和留出测试连起来#

配套源码新增 compiler/experiments/ai_tuning_demo.py，完整脚本只使用 Python 标准库，不需要模型账号、外部服务或加速设备。可从配套源码包取得，解压后在 compiler/ 目录运行：

python experiments/ai_tuning_demo.pypython experiments/ai_tuning_demo.py --output tuning-result.json

脚本的四个候选是 ijk、ikj，以及沿 k 轴分块的 k4、k8。它们都计算整数矩阵乘法，循环结构不同。输入元素固定在 -3 到 3，实验最大 n 为 28，所以每个点积的任意部分和绝对值不超过 28×9=252；此处可以精确比较结果，不涉及 int32 越界或浮点容差。

脚本先用独立的点积写法生成参考答案，逐元素验证每个将被测量的候选；验证通过才进入计时。候选会预热，随后分 7 轮测量，每轮每候选执行 3 次，并打乱候选顺序。输出保存每轮样本、中位数和 MAD，即“样本到中位数距离的中位数”。固定随机种子使输入和调度顺序可复现，不能使操作系统噪声消失。

训练形状为 12、16、20，验证形状为 24，最终测试形状为 28，集合先划分再采集标签。每个候选拟合一个极简模型 time(s,n)=α[s]×n³。下面摘出拟合和冻结步骤帮助阅读；这是完整脚本的一部分，不是可单独粘贴运行的程序。

# training[n][s]["median_ns"] 是训练形状上实际测到的标签。denominator = sum(n ** 6 for n in TRAIN)alpha = {    s: sum((n ** 3) * training[n][s]["median_ns"] for n in TRAIN)       / denominator    for s in SCHEDULES}predicted = min(SCHEDULES, key=lambda s: alpha[s] * VALIDATION ** 3)validation = measure(VALIDATION, ("ijk", predicted))model_ok = (    validation[predicted]["median_ns"]    < 0.97 * validation["ijk"]["median_ns"])selected = predicted if model_ok else "ijk"# 到这里冻结选择；最终测试只测基线和已选方案，不重新挑选赢家。test = measure(TEST, ("ijk", selected))

这是过原点最小二乘拟合，系数由训练标签求得，不是提前写死一个“获胜方案”。预先固定的验证门槛要求预测候选比基线的验证中位数快超过 3%，否则回退基线。这个门槛只是教学策略，不是统计显著性的判断。最终的 test_speedup 定义为“基线时间÷已选时间”，大于 1 才表示该点估计加速。

本次实际执行环境为 Windows、Python 3.14.4，脚本成功完成全部被测候选的精确结果检查。训练模型选中 ikj，验证阶段也接受它；最终测试得到：

n=28 的方案 中位耗时 MAD
基线 ijk 约 1.798 毫秒 约 0.033 毫秒
已选 ikj 约 1.829 毫秒 约 0.045 毫秒

本次 test_speedup≈0.983，没有测到加速；两者差异还与波动量级接近，不能据此宣称存在稳定回退。这正是保留测试集的价值：验证阶段看好的方案，不能靠修改最终答案来“变成成功”。你的机器可能得到另一个选择，基线被保留也是合法结果。

这个模型故意很弱：所有候选都只有一个乘 n³ 的系数，所以它对所有正 n 的排序相同，无法表达某个块大小只适合某个尺寸区间。训练和测试还属于同一种矩阵乘家族，不能证明跨程序泛化。更重要的是，测量对象是 Python 解释器循环，包含输出矩阵分配；列表索引和解释器开销很显著，结果不能外推到 C++、向量内核或加速设备。它展示实验方法，没有复现 MLGO 或张量编译器。

25.7 e-graph 与 equality saturation：同时保存多种表达方式#

普通重写器往往立即把 A 换成 B，之后某条规则是否还能应用取决于顺序。Equality saturation 的思路是保留多个等价表示，通过 e-graph 共享结构、合并等价类，再按代价抽取一个代表。egg 原论文介绍了使该流程高效并支持分析扩展的机制。egg 原论文

可以从纯数学整数表达式理解：a×2+a×3 与 a×5 属于一个等价集合；某台目标机器怎样实现它们，则由抽取代价决定。e-class 表示已知等价的一组形式，e-node 表示某个操作及其子等价类。结构共享避免逐个复制所有表达式，但不意味着搜索不会增长；时间、节点数和迭代预算仍然必要。egg 官方项目

它的关键前提是规则确实适用于当前语义。e-graph 能维护你加入的等价关系，不会替错误规则创造正确性证明。下面三类约束必须先处理：

  • 检查型整数。 Sprout 中 (x+1)-1→x 对最大 int32 不成立，左侧应报溢出。数学整数的结合、分配改写也可能改变中间溢出；需要区间或其他事实证明相关路径安全。
  • 浮点。 实数代数等式不一定保持舍入、NaN、无穷、带符号零或约定的异常行为。允许什么误差或放宽模式，应由语言与算子契约声明。
  • 副作用与陷阱。 把源表达式 E×0 改成 0，可能删去 E 中的打印、除零或其他可观察行为。若 E 已是一个可用的纯 SSA 值，消去乘法的条件又不同；此前产生 E 的有副作用或可能陷阱指令仍不能随意删除。

因此一个适合初学者的 e-graph 项目，是先仅处理无副作用、无限精度的纯表达式，明确规则集合；之后再加类型和区间分析。不要把一次合并误当成对整门语言、任意上下文的等价证明。抽取出的目标形式也要经过后端合法性检查，代价低不等于机器约束满足。

25.8 LLM 提出候选，外部流程负责验收#

大语言模型可以为优化序列排序、建议调度参数、生成候选改写或帮助缩小失败样例。2024 年的 LLM Compiler 原论文研究了编译器 IR、汇编及优化相关任务，是此方向的具体历史研究实例；论文中的特定任务结果不意味着任意 LLM 已经成为正确的通用优化器。LLM Compiler 原论文

给初次实验的模型一个很窄的输出接口，例如只允许返回 {"schedule":"ikj"}，候选必须来自白名单。宿主校验字段、枚举和预算，然后运行已有实现。再进一步让模型给出 pass 序列，也应只接受当前工具链真实存在的选项，记录完整序列和工具版本。

若允许直接改 IR，验收负担会明显增加。需要检查语法与类型、CFG/SSA 结构、目标指令约束，然后检查语义与性能。llvm-as 或结构验证器接受，只证明表示满足相应结构要求，不能证明减法没写反、陷阱没被删或内存别名没被忽略。

模型的解释可以帮助人工发现假设，但不能作为其输出正确的独立证据。“请保证完全等价”是一条请求，不是证明。即使模型生成证明文字，也需要能检查该性质的独立系统；同一模型再看一遍自己的答案，不能替代验证器。一个合理流水线是：候选提议→白名单/结构检查→语义检查与差分→性能复测→满足门槛才接受，否则保留基线。

还应把模型推理时间计入调优预算，保存模型版本、输入、采样设置和原始输出。相同提示不一定在所有服务与模型更新后产生相同结果；“固定随机种子”也不能替代固定模型与环境。对已有项目，先让模型选择现有候选，再研究开放式代码改写，往往更容易定位问题。

25.9 差分、容差与翻译验证各管什么#

整数实验应精确比较所有元素、输出顺序、成功/失败状态，以及必要的错误类别。只比较元素和或一个平均值会让位置交换、漏算和成对错误相互抵消。带副作用的程序还需要比较事件顺序，不能只比较最终返回值。

浮点任务常采用 |actual-reference|≤atol+rtol×|reference|，但阈值必须根据数据类型、算子与误差积累预先规定，并明确 NaN、无穷及特殊值策略。事后不断放大容差直到候选通过，相当于修改题目。通过容差测试说明这批输入满足数值标准，不是对所有输入的严格等价证明；容差也不能用来豁免整数溢出、越界或被删除的副作用。

翻译验证则尝试检查某次输入程序到输出程序的关系。Alive2 官方工具支持 LLVM 变换的 refinement 检查，并提供独立的 alive-tv；官方说明也列出不支持跨过程变换的边界。它不是任意语言、任意优化流水线的万能正确性证明器。Alive2 官方说明

这里尤其要防止语义丢失：如果把 Sprout 的“溢出必须报错”错误降低成未定义行为，再验证后面的 LLVM 变换，得到的结论也不会自动修复最初的降低错误。必须先证明或测试源语义被忠实表示。验证超时、工具不支持和发现反例也应分别记录，不能统一算成通过。

性能验证需要同样的耐心。记录硬件、系统、工具链、模型、选项、线程、输入生成方法和是否包含编译、分配或数据搬移；预热后重复测量，打乱或交错基线与候选顺序，保存原始样本。仅报告最快一次，容易把噪声当成优化；仅报告均值，也可能掩盖长尾和不同程序上的回退。

实验脚本用中位数和 MAD 是便于理解的起点，并未提供正式置信区间。更严肃的比较应增加独立运行、控制环境和适合的统计分析，报告逐工作负载结果及汇总方法。不要把某个训练机器上的单一“加速百分比”包装成对所有部署目标的保证。

25.10 常见错误、练习与验收#

常见错误是：让测试集参与挑选方案；把同一程序的改名副本当作独立样本；只验证输出形状；用模型得分代替实测；把 e-graph 合并当作规则证明；把 LLVM 的未定义行为当作 Sprout 的受控错误；只保留赢家数据，丢弃失败和回退。每一种都会使看似漂亮的结果失去解释力。

练习一：实验的 α[s]×n³ 模型为什么不能在 n=16 时选 k4、在 n=28 时选 ikj？怎样改进，同时保持最终测试独立？

参考答案

所有候选乘同一个正数 n³，排序只取决于 α，因而不会随 n 改变。可以加入形状与块大小交互特征，或使用分段模型；特征与超参数在训练/验证阶段选择，不能看完 n=28 的测试标签后继续把它称作未见测试。需要另留新形状评估改进后的最终模型。

练习二：模型建议将 print((x+1)-1); 改为 print(x);，并解释“加一减一抵消”。给出反例与需要证明的前提。

参考答案

取 x=2147483647，原 Sprout 程序必须在加一处报溢出，改写后会正常打印。至少要证明 x+1 不溢出，并保留 x 的求值及相关可观察行为，才能考虑该改写。数学恒等式本身不够。

练习三：验证集快 8%，测试集慢 2%，应修改哪个结果？

参考答案

都不修改，如实保留两个阶段的结果、样本和选择过程。先判断波动是否足以解释差异，再研究泛化或模型不足。若据此改模型，原测试集已经参与开发，下一轮应另设留出测试。

练习四：结构验证通过、100 次随机差分通过、翻译验证超时，能否写“优化已证明正确”？

参考答案

不能。可以分别报告结构检查通过、已测输入差分一致和翻译验证未完成。每项证据有自己的覆盖范围；超时不是反例，但也不是证明。对无法建立充分保证的候选，保留原程序或限制适用域。

本章验收：运行新增脚本并保存完整 JSON；能说明划分何时冻结、计时包含什么、系数从哪里来、最终加速比小于 1 表示什么；独立构造一个破坏结果的候选并确认它在计时前被拒绝；为一条 LLM 或 e-graph 改写列出类型、算术、副作用及验证前提。完成后，再把同一流程移植到一个真实 C++ 小内核，建立新的基线与测量记录，不能直接沿用 Python 的获胜结论。

如果还不熟悉调度参数如何改变执行顺序，可先打开张量分块交互实验，观察分块对矩阵乘法覆盖次序的影响。它帮助理解“候选方案是什么”；本章再解释怎样比较、选择和验证这些候选，交互演示本身不负责训练代价模型。
