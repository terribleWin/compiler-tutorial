CHAPTER 07 / 前端

第07章 递归下降：把表达式组织成树#

本章目标与前置#

你已经能把输入分成有种类和位置的 Token。本章从最小的整数表达式开始，构建一棵表达实际分组的树，再扩展到调用、语句、块和函数。完成后，你应该能解释优先级与结合性，写出不会无限递归的解析函数，并根据一个错误位置说明解析器当时期待什么。

参考工具的源码在 compiler/src/sprout.cpp。本章代码是分步说明算法的教学片段，不是对该文件的逐行复制；练习时先独立实现一个表达式解析器，再比较职责与数据流。

7.1 文法与调用栈如何对应#

考虑这条文法：primary = INTEGER | "(" expression ")"。解析器进入 primary 时，查看当前 Token。如果是整数，就消费它并返回整数节点；如果是左括号，就消费括号、递归解析内部表达式、要求右括号、返回内部树；否则报告缺少表达式。

每个非终结符对应一个解析函数，这就是递归下降的基本组织方式。函数调用栈天然记录“我在解析谁的内部”，因此可以处理任意有限深度的括号。实际工具还应限制极端嵌套，避免恶意输入耗尽宿主调用栈。

parsePrimary():    if match(Integer): 返回整数节点    if match(LeftParen):        value = parseExpression()        expect(RightParen, "括号表达式后需要 )")        返回 value    报错：当前位置需要表达式

这里解析不是求值。遇到 2 + 3 时，我们先保存它的结构，而不是立刻得出5。这样后续才能做类型检查、生成多个后端、输出树、优化或重新组织控制流。

7.2 为什么不能照抄左递归规则#

很自然的加法文法是 E → E + T | T。如果直接写成 parseE() 先调用 parseE()，还没消费任何 Token 就再次进入自身，会无限递归。解决办法之一是改写为：

addition = multiply { ("+" | "-") multiply } ;multiply = unary { ("*" | "/" | "%") unary } ;

先读一个左操作数，再循环吸收后面的运算符和右操作数。每次成功进入循环都至少消费一个运算符和一个表达式，因此能推进游标。它也自然产生左结合结构。

// 教学片段：假设 Expr、Binary、parseMultiply 等辅助类型已经定义。std::unique_ptr<Expr> parseAddition() {    std::unique_ptr<Expr> left = parseMultiply();    while (atPlus() || atMinus()) {        Token operation = advanceToken();        std::unique_ptr<Expr> right = parseMultiply();        std::unique_ptr<Expr> combined(            new Binary(operation, std::move(left), std::move(right)));        left = std::move(combined);    }    return left;}

这个片段先构造新的 unique_ptr<Expr> combined，再把 left 移动赋值为 combined，清楚分开“转移旧左树”和“替换根指针”，也方便调试。请勿把 AST 节点的引用交给会先销毁该节点的操作。

7.3 手算优先级与结合性#

输入 1 + 2 * 3 - 4，顶层调用 parseAddition：

  1. 第一次 parseMultiply 只读出整数1，因为后面是加号。
  2. 加法循环消费 +，再调用 parseMultiply。
  3. 这次乘法读出2，发现 *，再读3，返回 Multiply(2,3)。
  4. 加法把左树更新为 Add(1,Multiply(2,3))。
  5. 循环发现 -，读取4，最后得到 Subtract(Add(1,Multiply(2,3)),4)。

树的根是最后一步减法。这个结构表示 (1 + (2 * 3)) - 4，结果3。与之相比，8 - 3 - 1 若错误地递归读取右侧整个加法，会形成 8 - (3 - 1)，结果6。用非交换的运算符测试结合性，远比只测 1 + 2 + 3 有效。

一元规则可以递归：unary = "-" unary | "!" unary | primary。!-x 会先形成取负节点，再外包逻辑非节点；语法允许生成这棵树，但类型检查会发现不匹配。不要把“能造出树”误认为“这棵树必定有效”。

7.4 函数调用如何解析#

在主线语言中，名字后紧跟 ( 表示函数调用。参数列表是由逗号分隔的表达式，可能为空。解析调用时，先读名字，再读左括号；如果下一个不是右括号，就反复解析表达式并消费逗号；最后要求右括号。

f(1 + 2, g(3))Call f  argument 0: Add(Integer 1, Integer 2)  argument 1: Call g                argument 0: Integer 3

内部调用 g(3) 会完整消费自己的括号，外层才继续读取外层右括号。逗号不属于普通表达式运算符，所以表达式解析会在列表分隔处停下。若写成 f(1,)，逗号后面应继续要求一个表达式，而不是悄悄接受缺失参数。

递归下降可以通过少量向前查看处理共同前缀。以标识符开始的语句，可能是 x = ...;，也可能是 f(...);。参考语言把赋值限制为语句，因此可以查看名字后面是否是等号，决定进入赋值分支。不要为了这一个决定在所有地方都引入任意回溯。

7.5 从表达式扩展到语句与函数#

语句解析根据开头的关键字分派。let 解析名字、等号、初始化表达式和分号；return 解析返回表达式和分号；if、while 解析括号条件和块；左花括号进入嵌套块；其余路径尝试表达式语句或赋值语句。

块解析的循环条件是“还没看到右花括号，且没有到文件末尾”。不能只检查右花括号，否则缺失括号时可能越过 Token 数组末尾。循环结束后仍要 expect(RightBrace)，这样文件提前结束会得到明确错误。

函数解析负责读 fn、函数名、参数列表、箭头、返回类型和函数体。程序解析则不断读函数，最后确认消费 End Token。只解析一个函数然后忽略剩余输入，会错误接受两个程序拼接、尾随垃圾或截断输入。

7.6 遇到错误时保留语境#

对于 print(1 + );，错误地点是右括号附近，但原因是加号右侧需要表达式。好的诊断至少包含文件名、行列、发现的符号与期待的结构。不要统一返回“语法错误”四个字，也不要把当前 Token 游标倒退到整条语句开头，让使用者找不到缺口。

初学版本可以在第一个语法错误处停止。若要一次报告多个错误，可采用恐慌恢复：丢弃 Token，直到找到分号、语句开头关键字或合理块边界，然后继续。恢复必须与语法层次协调；把内层右花括号随意吃掉，会让外层再产生大量虚假错误。无论哪种策略，所有失败路径都必须保证停止或前进。

报错附近通常不应执行任何用户程序。解析器不是 REPL 求值器；即使前半段已经读到 print，发现后半段语法错误时也应阻止整个待编译程序进入执行阶段。

7.7 Pratt 与优先级爬升的另一种写法#

当运算符很多时，可以用优先级表驱动同一类解析逻辑。优先级爬升通常维护当前允许的最低优先级：读取左操作数，若下一个运算符优先级足够高，就读取它和右侧，再组合成新树。左结合运算在解析右侧时使用比当前更高的门槛，避免把同级运算全部吸到右边；右结合运算则使用适当的相同门槛。

Pratt 解析进一步把 Token 的前缀、后缀或中缀处理函数与绑定强度结合起来。它与分层递归下降都能正确处理表达式。第一次实现建议选择层次清楚的分层版本，等你能手算树形后再改成表驱动版本，并保留完全相同的测试。

7.8 实验、练习与验收#

给 main 分别加入下面几行，每次运行 --ast，观察结构而非计算结果：

print(8 - 3 - 1);print(8 - (3 - 1));print(1 + 2 * 3);print((1 + 2) * 3);

预期完整执行输出依次为4、6、7、9。前两行树的根都是减法，但右子树不同；后两行树的根分别是加法和乘法。

练习一：parseBlock 为什么不能看见文件结尾就当作正常结束？

查看答案

文件结尾可能说明用户漏写 }。把它当正常结束会接受不完整程序。循环应避免越界，但结束后仍要验证右花括号存在。

练习二：为优先级、结合性、嵌套调用各设计一个能区分正确与错误实现的测试。

查看答案

优先级用 1+2*3；结合性用 8-3-1；嵌套调用用 f(1,g(2,3))，并让函数结果依赖参数位置。只使用加法和相同参数，可能掩盖树形错误。

本章验收：能画出四个表达式的树，说明每个解析函数消费的 Token 范围，拒绝缺失操作数和未闭合块。下一章把手写解析器放到更完整的 LL、LR 与通用分析算法地图中。
